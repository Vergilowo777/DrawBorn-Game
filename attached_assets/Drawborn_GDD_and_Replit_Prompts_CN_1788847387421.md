# 《画灵：造物之战》游戏设计与 Replit 开发手册

**英文工作名：** Drawborn: Creator Clash  
**文档版本：** MVP 1.0  
**产品类型：** 2D 原创角色生成 + 剧情冒险 + 半自动战斗 + 异步 PVP  
**首发目标：** iOS App Store、微信小游戏  
**建议受众：** 13 岁以上、喜欢创作、角色养成和轻策略对战的玩家  
**核心宣传语：** 你画下的英雄，真的会为你而战。

> 最重要的产品决定：玩家的画决定角色的身份与外观，玩家的选择决定战斗方式，系统规则决定公平性。AI 只提供理解、推荐和表现，不直接决定强弱。

## 1. 产品结论

《画灵：造物之战》的独特价值不是“AI 画图”，而是“玩家亲手创造的角色能够被理解、培养、战斗和展示”。游戏需要同时成立四种体验：

- 创造感：这是我画出来的角色。
- 被理解感：系统理解了我画的武器、元素和性格。
- 成长感：角色会升级、获得装备并改变战斗方式。
- 展示感：别人能够看到并挑战我的原创角色。

第一版不制作大型实时动作 PVP，不允许 AI 随意生成数值和技能，不把公开角色交易、实时聊天、抽卡付费加入 MVP。先证明“创造角色 -> 完成首战 -> 愿意继续培养”的核心乐趣。

## 2. 世界观与剧情

画界曾经由无数“造物师”共同绘制。一天，一股被称为“空白潮”的力量开始擦除颜色、名字和记忆。玩家是新一代造物师，能够让自己的画作获得生命，并进入不同画卷世界找回失落的色彩。

### 第一章：被擦除的铅笔镇

- 场景：铅笔线条组成的小镇，部分建筑正在消失。
- 普通敌人：橡皮兽、断线虫、墨渍团。
- 精英敌人：褪色骑士。
- 章节 Boss：巨型擦除者“无痕”。
- 章节奖励：第一件元素装备、角色外观进化槽、竞技场资格。

后续可扩展为水彩森林、涂鸦都市、水墨古城、像素王国和机械画布。不同画风不需要强行统一，它们就是世界观的一部分。

## 3. 核心游戏循环

1. 玩家在画布中画出角色。
2. 系统先进行内容安全检查，再识别角色的视觉特征。
3. AI 推荐名字、背景、职业、元素、战斗风格和技能候选。
4. 玩家确认或修改推荐结果，得到第一版角色。
5. 玩家完成剧情关卡，获得金币、颜料、经验和装备。
6. 玩家调整技能、天赋和装备，形成战斗构筑。
7. 玩家挑战异步竞技场中的其他玩家角色。
8. 玩家解锁新画笔、特效和进化部件，再次创作或强化角色。

单次普通关卡建议 2 至 4 分钟；首次从打开游戏到开始第一场战斗不超过 5 分钟。

## 4. 首次用户体验

### 4.1 新玩家流程

1. 开场动画展示空白潮擦除世界，时长不超过 20 秒，可跳过。
2. 直接进入访客模式，不强制注册。
3. 用 3 个画笔引导动作教玩家画出头部、身体和武器。
4. 系统展示“我看到了什么”，而不是直接宣布结果。
5. 玩家从 3 个职业建议、2 个元素建议和 3 个技能中选择。
6. 立即进入 60 至 90 秒的教学战斗。
7. 战斗结束后再提示绑定 Apple、微信或其他平台账号。

### 4.2 角色创建画布

首版采用固定 1:1 画布和轻量引导骨架，不尝试把任意复杂画作自动绑定成完整骨骼动画。

- 画布尺寸：逻辑尺寸 1024 x 1024，显示时自适应屏幕。
- 工具：铅笔、马克笔、橡皮擦、撤销、重做、颜色、线宽、清空。
- 引导层：头部区域、身体区域、左右手区域和武器区域，可关闭。
- 保存：保存原始笔画数据、合成 PNG 和缩略图。
- 可访问性：提供高对比度色板和色盲友好元素图标。
- 防误操作：清空需要二次确认；离开画布自动保存草稿。

### 4.3 AI 识别确认页

系统输出只能作为建议，所有结果均可修改。页面显示：

- “我识别到”：剑、面具、红色火焰、轻甲等标签。
- 推荐职业：3 选 1。
- 推荐元素：2 选 1，也可打开全部元素。
- 推荐战斗风格：爆发、控制、防御或持续输出。
- 技能候选：3 选 1。
- 名字与背景：可编辑、重新生成或完全跳过。

如果识别失败，系统提供“我来告诉你”入口，让玩家手动选择标签，不阻断创建流程。

## 5. 角色系统

### 5.1 五种职业

| 职业 | 定位 | 核心特点 | 上手难度 |
|---|---|---|---|
| 先锋 | 均衡近战 | 稳定伤害、短距离突进 | 低 |
| 影刃 | 爆发刺客 | 高机动、连击、低耐久 | 高 |
| 灵弦 | 远程输出 | 风筝、蓄力攻击 | 中 |
| 秘术 | 范围控制 | 元素区域、减速、打断 | 中 |
| 守誓 | 防御反击 | 护盾、格挡、反伤 | 低 |

### 5.2 四种首发元素

- 火：叠加灼烧，强调持续伤害。
- 冰：降低速度，强调控制节奏。
- 雷：干扰能量，强调打断技能。
- 生：恢复或吸取少量生命，强调续航。

首版不做固定的元素克制环，避免新玩家背诵规则。元素提供不同打法，而不是简单增加伤害。

### 5.3 战斗属性

基础属性为生命、攻击、防御、速度和能量效率。每个职业使用固定属性预算，AI 不得增加预算。玩家画十把剑也不会得到十倍攻击力。

每个角色拥有：

- 1 个自动普通攻击。
- 2 个主动技能。
- 1 个终极技能。
- 1 个被动天赋。
- 3 个装备槽：武器、护具、核心。

## 6. 战斗设计

### 6.1 战斗形态

采用横向 2D 半自动即时战斗：角色自动移动并进行普通攻击，玩家控制两个技能、终极技能和一次防御/闪避。PVE 和 PVP 共用同一套战斗模拟器。

- 单局时长：2 至 4 分钟。
- 技能采用能量和冷却双重限制。
- 命中、暴击和状态效果使用带种子的确定性随机数。
- 竞技场为异步 PVP：对手使用其保存的防守构筑，由系统 AI 控制。
- 战斗结束后提供 15 秒关键回放和伤害构成。

### 6.2 初始数值公式

伤害公式建议：

`damage = max(1, attacker.attack × skillMultiplier × 100 / (100 + defender.defense) × statusModifier)`

其中随机波动限制为正负 3%，PVP 使用服务器生成的 battleSeed。最终结果由服务器按同一规则复算，客户端只负责表现，避免修改本地数值作弊。

### 6.3 PVP 公平原则

- 排位赛统一到标准等级，装备按竞技属性模板换算。
- 高等级玩家获得更多构筑选择，不获得无限数值碾压。
- 付费内容不增加竞技基础数值。
- 每个版本记录职业胜率、技能使用率、平均战斗时长和先手胜率。
- 单一职业整体胜率连续显著偏离目标区间时进入平衡复查，而不是立即根据少量投诉修改。

## 7. PVE 与成长系统

### 7.1 第一版内容

- 1 个剧情章节，共 10 个关卡。
- 3 种普通敌人、2 种精英敌人和 1 个 Boss。
- 5 个可重复挑战的材料关卡。
- 20 件装备、20 个技能、10 个天赋。
- 1 个训练场，可测试技能和伤害。

### 7.2 资源

- 金币：升级 PVE 装备与技能。
- 颜料：解锁颜色、线条和外观特效。
- 灵感：用于角色外观进化，不影响竞技数值。
- 经验：提升 PVE 等级。

### 7.3 角色进化

角色达到关键阶段后，玩家不是点击“自动进化”，而是重新进入原画，在受控区域添加翅膀、盔甲、武器或纹章。系统保存多个成长形态，玩家可以随时回看。

## 8. 装备与技能

装备主要改变打法和表现，不只增加攻击数字。例如：

- 雷鸣核心：技能命中后削减对方少量能量。
- 纸盾披风：首次生命低于 40% 时生成护盾。
- 回声长刃：连续使用不同技能后强化下一次普通攻击。
- 水彩瓶：受到控制效果后短暂提高速度。

首版装备通过剧情、关卡和成就获得。MVP 不出售随机装备箱，不做付费抽卡。

## 9. 页面与信息架构

| 页面 | 主要功能 | 首版优先级 |
|---|---|---|
| 启动与访客入口 | 加载、协议、访客模式、账号绑定 | P0 |
| 主城 | 继续剧情、角色、竞技场、任务入口 | P0 |
| 创作画布 | 绘画、草稿、提交识别 | P0 |
| AI 确认 | 标签、职业、元素、技能和背景确认 | P0 |
| 剧情地图 | 章节和关卡选择 | P0 |
| 战斗 | 半自动战斗和技能操作 | P0 |
| 结算 | 奖励、经验、关键表现 | P0 |
| 角色详情 | 属性、技能、装备、进化 | P0 |
| 异步竞技场 | 对手列表、挑战、段位 | P1 |
| 作品画廊 | 展示、点赞、举报、屏蔽 | P2 |
| 商店 | 纯外观商品、订单恢复 | P2 |

主城底部导航建议只保留“冒险、创作、角色、竞技”四项，商店和设置放到二级入口。

## 10. 美术与交互方向

选用“水彩幻想 + 铅笔线稿”作为主视觉：背景像翻开的画册，UI 卡片带有轻微纸张纹理，角色保留玩家原始笔触，技能效果用颜色扩散和墨迹飞溅表现。

- 主色：深墨蓝 `#253248`。
- 强调色：灵感金 `#F2B84B`。
- 画布背景：暖纸白 `#F6F0E4`。
- 危险色：擦除红 `#D95757`。
- 成功色：生命绿 `#4FA87B`。
- 字体：中文使用清晰无衬线字体，标题可使用少量手写风格，但正文禁止手写体。
- 动效：按钮压感、纸张翻页、颜色扩散；避免持续闪烁和过强粒子。

角色战斗表现采用“原画立绘 + 分层浮动 + 武器轨迹 + 命中特效”的方式。第一版不承诺任意画作的复杂骨骼动画。

## 11. AI 功能边界

### AI 可以做

- 从画作中提取安全的视觉标签。
- 推荐职业、元素和预设技能。
- 生成可编辑的角色名字与短背景。
- 生成角色精修预览，但必须同时保留原画模式。
- 对公开展示内容做预审和风险评分。

### AI 不可以做

- 自由生成未经系统验证的战斗数值或技能代码。
- 根据绘画复杂程度决定角色强弱。
- 在客户端直接调用模型并暴露密钥。
- 未经玩家确认就公开或训练使用玩家作品。
- 在审核失败时只显示模糊的“系统错误”。

AI 输出使用结构化 JSON，并由服务器执行 schema 校验、枚举过滤和数值裁剪。模型返回的任何技能 ID 必须已经存在于 `SkillDefinition` 表中。

## 12. 内容安全与版权

玩家画作、角色名、角色背景和公开展示内容均属于用户生成内容。发布前必须具备：

- 上传前和上传后的内容过滤。
- 举报入口、举报原因和处理状态。
- 屏蔽用户功能。
- 客服与公开联系信息。
- 违规内容下架、账号限制和申诉流程。
- 针对年龄不适内容的标记与年龄限制。
- 相似知名角色提示和版权投诉通道。

建议将公开展示与私密使用分开：角色可以先在个人剧情中使用，只有通过公开审核后才能进入竞技场对手池和作品画廊。

面向中国大陆提供 AI 生成或合成内容时，产品需要按照适用规则实现显式/隐式标识能力。建议在精修图详情中显示“AI 辅助生成”，并在文件元数据或服务端记录中保留生成来源、模型版本和内容 ID。正式上线前应由熟悉游戏出版、未成年人保护和生成式 AI 合规的专业人员复核。

## 13. 商业化原则

首版先验证留存，不急于变现。第二阶段可加入：

- 画笔、纸张纹理和颜色包。
- 技能视觉特效，不改变技能数值。
- 角色展示框、入场动画和胜利动作。
- 剧情扩展包。
- 赛季通行证，但免费玩家也能完成核心成长。

iOS 内解锁数字功能、游戏货币、关卡和外观需要按 Apple 当前规则接入 In-App Purchase。若以后出售随机虚拟物品，必须在购买前显示概率；本方案建议首发完全不做付费随机箱。

## 14. 技术架构

### 14.1 推荐方案

- 游戏客户端：Cocos Creator 4.0 LTS + TypeScript，2D 模式。
- 后端：Node.js + TypeScript + Fastify 或 Express。
- 数据库：PostgreSQL + Prisma。
- 文件：对象存储保存原画、缩略图、精修图和回放摘要。
- 缓存/队列：早期可用数据库任务表，规模增长后接 Redis 和任务队列。
- AI：通过服务端 `AIProvider` 接口接入可用的视觉、文本和审核服务。
- 日志：结构化日志，记录 requestId、userId、battleId 和 aiJobId，禁止记录完整密钥和敏感原图。

Cocos Creator 官方支持 Web、原生和小游戏平台构建，适合同时面向 iOS 与微信小游戏。微信小游戏不等同于浏览器环境，因此不要把普通 React 网页或 React Native/Expo 项目当作可直接转换的微信小游戏生产代码。

### 14.2 Replit 的正确角色

Replit 用于：

- 生成和修改 TypeScript 游戏脚本。
- 开发后端 API、数据库和管理工具。
- 运行单元测试、接口测试和 Web 管理台。
- 管理环境变量、开发数据库和对象存储。
- 与 GitHub 同步代码。

本地 Mac 用于：

- 使用 Cocos Creator 打开和预览游戏工程。
- 使用微信开发者工具调试 `wechatgame` 构建。
- 处理 iOS 证书、真机测试和最终提交流程。

不要要求 Replit 一次性“生成完整商业游戏并直接上架”。按照本手册后面的阶段提示词逐步实现，每阶段通过验收后再进入下一阶段。

### 14.3 平台适配层

定义统一接口：

- `AuthAdapter`：Guest、Apple、WeChat。
- `PaymentAdapter`：Apple IAP、WeChat 支付。
- `ShareAdapter`：iOS 分享、微信转发。
- `StorageAdapter`：本地缓存、云端同步。
- `AnalyticsAdapter`：统一事件名，不在业务代码中直接调用平台 SDK。

### 14.4 微信小游戏资源策略

微信小游戏不是浏览器环境，平台 SDK 需要单独适配。主包只放启动场景、基础 UI、首战资源和必要代码；章节背景、语音、高清角色图和后续关卡使用 Asset Bundle 与远程资源。当前 Cocos 4.0 文档说明微信小游戏主包不能超过 4 MB，额外资源需网络下载，且不能远程下载脚本，因此功能代码必须随合法代码包发布。

## 15. 数据模型

核心表建议：

- `User`：账号状态、地区、年龄声明、创建时间。
- `AuthIdentity`：guest、apple、wechat 等登录身份。
- `PlayerProfile`：昵称、头像、设置和段位。
- `Hero`：角色职业、元素、等级、状态和拥有者。
- `HeroArtwork`：原始笔画、原图、缩略图、精修图、AI 标识和公开审核状态。
- `HeroBuild`：技能、天赋、装备和竞技标准化快照。
- `SkillDefinition`：服务端认可的技能模板。
- `EquipmentDefinition`：装备模板、效果和版本。
- `InventoryItem`：玩家拥有的物品和数量。
- `AdventureProgress`：章节、关卡星级和奖励领取状态。
- `Battle`：模式、种子、版本、双方快照和结果。
- `ArenaDefense`：玩家当前公开防守构筑。
- `AIJob`：识别、文本、精修和审核任务状态。
- `ContentReport`：举报对象、原因、证据和处理结果。
- `BlockRelation`：用户屏蔽关系。
- `Purchase`：平台订单、商品、校验和退款状态。

所有货币、奖励、战斗结算和购买结果由服务端作为最终权威。客户端不得直接提交“增加金币”或“胜利结果”。

- `POST /v1/auth/guest`
- `POST /v1/auth/platform`
- `POST /v1/account/bind`
- `DELETE /v1/account`
- `POST /v1/artworks/upload-url`
- `POST /v1/heroes/analyze`
- `GET /v1/ai-jobs/:id`
- `POST /v1/heroes`
- `GET /v1/heroes/:id`
- `PATCH /v1/heroes/:id/build`
- `GET /v1/adventure/chapters`
- `POST /v1/battles/pve/start`
- `POST /v1/battles/pve/finish`
- `GET /v1/arena/opponents`
- `POST /v1/arena/challenge`
- `PUT /v1/arena/defense`
- `POST /v1/content/report`
- `POST /v1/users/:id/block`
- `POST /v1/purchases/verify`

使用 OpenAPI 生成接口文档。所有写接口增加幂等键、速率限制、鉴权和 schema 校验。

```text
    api/                  # Node.js TypeScript API
    admin-web/            # 内容审核与运营后台
  packages/
    battle-core/          # 纯 TypeScript 确定性战斗模拟器
    contracts/            # DTO、枚举与 Zod schema
    game-data/            # 技能、装备、关卡配置
    platform-adapters/    # 平台接口定义
  docs/
    GDD.md
    API.md
    CONTENT_SAFETY.md
    RELEASE_CHECKLIST.md
  tests/
```

`battle-core` 禁止依赖 Cocos、DOM 或 Node 专属 API，使其可以同时运行在客户端、服务端和测试环境。

## 18. MVP 范围

### 必须完成

- 绘画、保存草稿和角色创建。
- 模拟 AI 或真实 AI 的结构化角色建议。
- 玩家确认职业、元素和技能。
- 一个完整剧情章节和 Boss。
- 半自动战斗、结算和成长。
- 角色详情、装备和技能配置。
- 异步 PVP 最小版本。
- 内容审核、举报、屏蔽、隐私与账号删除入口。
- iOS 和微信小游戏平台适配骨架。

### 明确不做

- 实时联网 PVP。
- 自由交易市场。
- 玩家之间的文字或语音聊天。
- 公会战和大型世界 Boss。
- 3D 角色和任意骨骼自动绑定。
- 付费抽卡和随机装备箱。
- AI 自由生成战斗代码。

| 阶段 | 目标 | 参考周期 | 核心验收 |
|---|---|---|---|
| 0 | 仓库、规范、共享类型 | 2-4 天 | 测试、lint、CI 全绿 |
| 1 | 绘画到角色确认 | 1-2 周 | 草稿恢复、识别失败可手选 |

| 3 | 剧情与成长 | 2-3 周 | 10 关、Boss、装备与存档 |
| 4 | 后端与异步 PVP | 2-3 周 | 服务端复算、对手与段位 |

## 20. 数据指标

首版只追踪帮助改进产品的必要事件，并在隐私政策中如实披露。建议关注：

- 开始绘画率、完成绘画率。
- 从完成绘画到确认角色的转化率。
- 首战开始率和首战完成率。
- 首日完成关卡数。
- D1、D7 留存。
- 每周创建角色数和竞技参与率。
- AI 识别修改率与失败率。
- 举报率、审核通过率和处理时长。
- 职业胜率、技能选取率和平均对局时长。

内部初始目标可设为：角色创建完成率不低于 65%、创建后首战开始率不低于 70%、D1 留存不低于 30%。这些是产品验证目标，不是市场保证，应根据真实数据调整。

## 21. App Store 发布路线

1. 先通过本地真机和 TestFlight 完成封闭测试。
2. 准备 Apple Developer Program、Bundle ID、证书和 App Store Connect 记录。
3. 在应用内和商店元数据中提供隐私政策链接。
4. 如果允许创建账号，必须在应用内提供账号删除。
5. 由于角色画作属于 UGC，提供过滤、举报、屏蔽和公开联系信息。
6. 数字商品使用 Apple IAP，并支持适用的恢复购买流程。
7. 商店截图必须来自真实游戏，不出现调试界面或未经授权的知名角色。
8. 审核备注说明画作审核、AI 处理、PVP 和付费的完整操作路径，并提供审核账号或可重复测试方式。

建议首发不要选择 Kids Category，也不要在名称和宣传中使用“专为儿童”等表述。正式年龄分级应根据实际暴力、UGC 和社交能力填写问卷确定。

## 22. 微信小游戏发布路线

1. 在微信公众平台创建小游戏并取得 AppID，确认主体和目标类目可用。
2. 使用 Cocos Creator 构建 `wechatgame`，再用微信开发者工具真机预览。
3. 接入微信登录、转发、支付和隐私授权的平台适配层。
4. 控制主包体积，将非首屏资源配置为分包或远程 Asset Bundle。
5. 准备用户协议、隐私保护指引、客服、内容安全、未成年人保护和投诉机制。
6. 通过体验版进行兼容、弱网、冷启动、内存和支付测试。
7. 提交平台审核并根据当前后台要求补充资质。

中国大陆网络游戏公开运营涉及出版审批等要求。国家新闻出版署的国产网络游戏审批材料明确区分移动游戏类别并要求出版单位、运营机构等信息。因此，不能假设个人主体、Replit 项目和一个微信 AppID 就足以完成商业上线。建议开发早期就联系具备经验的国内游戏发行或出版合作方，根据实际玩法、收费方式和发行地区确认版号、主体、备案、未成年人保护及其他资质安排。

## 23. 推广方案

### 23.1 可传播的产品机制

- 每次创建完成自动生成“原画 -> 角色卡 -> 战斗瞬间”分享卡。
- 分享卡只展示审核通过的内容，不泄露用户真实信息。
- 每周创作主题，例如“只用三种颜色画英雄”。
- 好友挑战链接直接打开对手预览和试玩入口。
- 战后生成 8 至 12 秒竖屏高光视频，方便视频号、抖音、小红书和 Bilibili 发布。

### 23.2 冷启动活动

第一轮邀请 50 至 100 名种子玩家，分为绘画爱好者、轻度游戏玩家和普通用户。活动主题为“把小时候画过的英雄复活”。收集他们完成角色所需时间、识别错误、首战感受和愿不愿分享。

### 23.3 内容计划

- 周一：本周创作主题。
- 周三：玩家角色改造前后对比。
- 周五：角色竞技场挑战。
- 周末：Boss 共创或世界观投票。

宣传不得使用未经授权的动漫、游戏角色作为主要素材，不使用“AI 保证生成最强角色”“充值即可碾压”等误导性表达。

## 24. 正式 Replit 主提示词

将下面内容先发送给 Replit。它的作用是建立长期项目规则，不要求一次完成全部功能。

```text
你是本项目的资深游戏工程师、后端工程师和测试负责人。我们正在开发一款暂定名为《画灵：造物之战 / Drawborn: Creator Clash》的 2D 跨平台游戏。

核心体验：玩家在画布中亲手画角色；系统识别武器、元素和风格并推荐职业与预设技能；玩家确认后进入剧情冒险、装备成长和异步 PVP。AI 只允许推荐既有枚举、文本和视觉表现，不允许生成自由战斗代码或越过数值预算。

生产目标：iOS App Store 与微信小游戏。游戏客户端使用 Cocos Creator 4.0 LTS + TypeScript；后端使用 Node.js + TypeScript + PostgreSQL + Prisma；共享 battle-core 必须是纯 TypeScript，不依赖 DOM、Cocos 或 Node 专属 API。

仓库结构：apps/game-client、apps/api、apps/admin-web、packages/battle-core、packages/contracts、packages/game-data、packages/platform-adapters、docs、tests。

硬性规则：
1. 先检查现有仓库和文档，不覆盖已有用户修改。
2. 每次只实现我当前要求的阶段，不提前扩展。
3. 任何密钥只能放服务端环境变量，禁止写入客户端、日志、README 或提交记录。
4. 战斗、奖励、货币和购买结果以服务端为准；客户端只提交操作输入。
5. AI 输出必须经过 JSON schema、枚举白名单和数值裁剪；技能 ID 必须来自 game-data。
6. 角色画作公开前必须有审核状态；预留举报、屏蔽、客服联系和账号删除。
7. 平台能力必须通过 AuthAdapter、PaymentAdapter、ShareAdapter、StorageAdapter、AnalyticsAdapter 接入。
8. TypeScript 开启 strict；所有公共函数有类型；核心规则写单元测试。
9. 每阶段结束时运行 lint、typecheck、test，并给出变更文件、测试结果、遗留问题和下一步建议。
10. 遇到不确定的平台 API 时先建立接口和 mock，不伪造已经成功发布或支付。

暂时不要编写全部游戏。先回复：你理解的架构、主要风险、需要检查的本地环境和阶段 0 实施计划。等我确认后再开始。
```

## 25. Replit 分阶段提示词

### 阶段 0：仓库与基础规范

```text
现在执行阶段 0。建立 pnpm workspace/monorepo、TypeScript strict、ESLint、格式化、Vitest 和基础 CI。创建约定目录与 README，不实现具体游戏 UI。建立 packages/contracts、battle-core、game-data、platform-adapters 的最小可编译骨架；为职业、元素、技能 ID、装备 ID、BattleSeed、BattleSnapshot 定义类型和 Zod schema。创建 .env.example，但不要生成或填写真实密钥。完成后运行 lint、typecheck、test，并停止等待验收。
```

### 阶段 1：绘画与角色确认

```text
现在执行阶段 1。实现 Cocos Creator 侧的绘画数据模型和控制器：画笔、橡皮、撤销、重做、清空确认、草稿自动保存、PNG 导出接口。先使用 MockHeroAnalyzer 返回结构化建议，不接真实 AI。实现标签确认、职业三选一、元素二选一、技能三选一和手动修正流程。识别失败时必须允许玩家继续。为 stroke 序列化、草稿恢复、schema 校验和枚举过滤编写测试。不要实现 PVP。
```

### 阶段 2：战斗垂直切片

```text
现在执行阶段 2。先在 packages/battle-core 实现确定性战斗模拟器，再接入 Cocos 表现层。包含普通攻击、能量、冷却、两个主动技能、终极技能、闪避/防御、火冰雷生四种状态效果、胜负与超时判定。相同 battleSeed 和输入序列必须产生相同结果。创建先锋和秘术两个可玩职业、三个敌人和一个 90 秒教学战。至少覆盖伤害、防御、冷却、状态、同种子复现和非法输入测试。
```

### 阶段 3：剧情、成长与存档

```text
现在执行阶段 3。实现第一章 10 个关卡、关卡配置加载、奖励、经验、金币、装备、角色详情和本地/服务端存档接口。先使用配置化敌人和占位美术。奖励领取必须幂等，不能通过重复提交结算增加货币。完成章节地图、关卡进入、战斗、结算、强化和再次挑战的完整闭环。
```

### 阶段 4：后端与异步 PVP

```text
现在执行阶段 4。在 apps/api 中实现访客账号、账号绑定预留、角色、背包、进度、战斗和竞技场 API。使用 PostgreSQL + Prisma。客户端请求挑战后，服务器创建 battleSeed、读取双方不可变快照、运行 battle-core 复算并保存结果。实现对手列表、防守构筑、简单段位分和基础限流。为越权访问、重复结算、伪造货币、失效快照和幂等键编写集成测试。
```

### 阶段 5：真实 AI 与内容安全

```text
现在执行阶段 5。设计 AIProvider、ContentModerator、HeroAnalyzer、StoryGenerator 接口。先实现可替换 provider 和 mock，再根据已配置的服务端环境变量接入一个真实供应商。AI 任务必须异步化，包含 queued/running/succeeded/failed/blocked 状态、超时、重试和降级。输出只允许白名单职业、元素、视觉标签和技能 ID。实现原画私密状态、公开审核状态、举报、屏蔽和审核后台最小版本。禁止把任何模型密钥发送给客户端。
```

### 阶段 6：平台适配与发布准备

```text
现在执行阶段 6。实现 Guest/Apple/WeChat 的 AuthAdapter 骨架，Apple IAP 与微信支付的 PaymentAdapter 骨架，iOS/微信分享适配，以及隐私、账号删除、客服、举报和恢复购买入口。平台暂时不可调用时使用显式 mock，并标记 TODO，不伪造成功。准备 Cocos 的 iOS 与 wechatgame 构建配置、远程 Asset Bundle 方案和发布检查清单。检查首场景依赖和微信主包体积，给出真机测试步骤。
```

### 阶段 7：上线前测试

```text
现在执行阶段 7。建立上线前测试矩阵：首次启动、访客模式、账号绑定、弱网、AI 超时、草稿恢复、内容拦截、10 关剧情、装备、异步 PVP、举报屏蔽、删除账号、购买恢复、不同屏幕比例、微信冷启动、iOS 真机内存。修复 P0/P1 缺陷，生成 RELEASE_CHECKLIST.md、PRIVACY_DATA_MAP.md、APP_REVIEW_NOTES.md 和 WECHAT_SUBMISSION_NOTES.md。不要声称审核一定通过。
```

## 27. 决策与下一步

当前应该先完成阶段 0 至阶段 2，得到一个可玩的“绘画 -> 确认 -> 首战”垂直切片，再邀请种子玩家测试。只有当玩家愿意完成角色并开始第二场战斗时，才值得继续投入完整剧情、AI 精修和 PVP 后端。

最先验证的三个问题是：

1. 玩家是否觉得系统真的理解了自己的画？
2. 角色原始画风是否在战斗中被保留下来？
3. 第一场战斗后，玩家是否想继续培养或分享这个角色？
